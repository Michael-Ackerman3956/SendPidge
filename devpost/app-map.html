Snapshot of commit 7d33a7f (2026-10-26). Code moves; paths and symbols below were checked against that commit and can drift.

What it is

An inbox that asks the real person. When an email to Grandma claims to be from someone in her circle and asks for money, a code or an urgent action, Pidge holds it and asks that person (Jimin) on a channel only he controls: the SendPidge app or WhatsApp. His answer, not a score, decides what Grandma sees.

Four pieces: mail in (Amazon SES Mail Manager writes each email to S3), the Reader (a Lambda runs a tool-less Strands agent on Claude through Amazon Bedrock, then a policy written in code decides hold / warn / pass), the ask and the answer (DynamoDB rows, an API Gateway WebSocket to both PWAs, WhatsApp through AWS End User Messaging Social), and Pidge the case agent (Amazon Bedrock AgentCore, woken by a DynamoDB stream after a verdict to write the case note). Everything is declared in one AWS CDK stack.

One action, followed through

The scam scene: a fake "Jimin" email arrives, Grandma sees a hold, Jimin taps No, Grandma sees "Not from Jimin".

Route (reference, three stops)

Toured in chat on 2026-10-26 as one-sentence explanations of the files below, not by clicking through a running editor.

  1. Entry: lambda/pidge_reader/handler.py, function process_email_object. Reads the S3 object, runs the Reader, then policy.decide (in lambda/shared/policy.py) turns the Reader's verdict plus the contact lookup into HOLD, WARN or PASS. A HOLD calls hold_and_ask, which writes the request row and asks Jimin.
  2. Logic: lambda/pidge_verdict/handler.py, function handle. Every tap from either PWA (WebSocket) or from WhatsApp (SNS) lands here and is routed by the ClientAction enum to record_answer in lambda/shared/verdict.py. The user is taken from the connection row, never from the message body; the rules (No beats Yes, undo window, expected sender only) live in verdict.py and are proven by lambda/tests/test_verdict.py.
  3. Result: pwa/js/verdict-view.js, functions deriveEmailDisplayState and buildRowStatusChipElement. The pushed request state becomes the chip Grandma reads ("Held · checking with Jimin", "Not from Jimin", "Jimin confirmed") and showDeniedVerdictOverlay is the press-and-hold Confirm sheet.

A practice to reuse

State the expected outcome of a check before running it, in a form the run itself can judge. scripts/swarm.py asserts, per email, "held or warned" versus "wrongly held" against the deployed pipeline. Its first live run (2026-10-25, run b7bffe) reported a false FAIL on the gift control: a hold past the ask cap is stored as warn ask_capped, and the checker had not been told that a capped hold is still a hold. The fix was in the checker (lambda/tests/test_swarm.py, test_a_capped_hold_is_stored_as_warn_ask_capped_and_still_counts_as_a_hold), and the second run passed 8 of 8 attacks held or warned, 0 of 2 controls wrongly held. The same move works on any project: write the sentence the result must satisfy, make the run print pass or fail against it, and treat a surprising FAIL as a question about either the code or the sentence, not as noise.
