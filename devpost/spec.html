How This Works

SendPidge is a PWA (a website that installs like an app) with an AI agent called Pidge. When an email arrives claiming to be someone you know and asking for money, Pidge holds it and asks the real person "was this you?" on a channel only they control. Their answer lands on your screen in seconds.

Inside AWS: Amazon SES Mail Manager receives the email and writes it to S3. A Strands agent on AWS Lambda reads it with Claude Haiku 5.5 on Amazon Bedrock and returns a typed verdict. That reader has no tools — it only ever sees the untrusted text. Plain code then checks the DynamoDB trust graph, creates a 10-minute hold (one re-ask interval), and fans out the question in parallel over AWS End User Messaging SMS (RCS), AWS End User Messaging Social (WhatsApp) and an in-app WebSocket. The reply comes back through Amazon SNS (WhatsApp) or the WebSocket (in-app), a second Lambda records the verdict, and Amazon API Gateway WebSocket pushes it to Grandma's screen.

After the verdict, a second Strands agent — the Pidge case agent on Amazon Bedrock AgentCore Runtime with AgentCore Memory — reads only the structured case row (and, when Grandma asks it something in the chat window or by mail, her question plus the held-mail metadata), remembers the family's history, writes the case note, sends Jimin a receipt and drafts the recovery pack. It never sees the email body and contacts no third party.

The agent is autonomous — nobody asks it to check — but the decision to hold or release is code, not a prompt. That is why Pidge can't be talked into releasing. A code-driven gate catches impersonation (known name + unknown address) without any model. On a hold with an unknown address a second model (Claude Opus) gets the facts code gathered plus the email, and returns hold or warn; code applies it only to the model-driven gate, never to the code-driven one, and any failure stays a hold. Grandma can also ask Pidge in a chat window or by mailing pidge@: her words pass Bedrock Guardrails, then the case agent answers from her own rows only. The ask shows sender address and subject from code, not from the model's summary. Impersonator payment asks require two taps; authenticated senders get one. A Yes has a 10 s undo window; a No can be reversed within 5 min.

Agent Layer — Strands Agents SDK

Rule of Two (your 2026-10-03 ruling, same as Meta's agent rule): the model that reads untrusted text gets no tools; code runs lookups and sends; the AI can only raise a verdict. Strands expresses this directly — Agent(tools=[]) with a Pydantic structured_output_model. The structured-output schema is itself a side-effect-free validating tool.

from pydantic import BaseModel, Field
from typing import Literal
from strands import Agent
from strands.models import BedrockModel

class EmailVerdict(BaseModel):
    claimed_person: str | None = Field(description="Name the sender claims to be, or null")
    intent: Literal["money", "code", "urgent_action", "none"]
    confidence: float = Field(ge=0, le=1)
    summary: str = Field(max_length=140, description="One neutral sentence for the real person. No URLs, numbers or instructions.")

reader = Agent(
    model=BedrockModel(model_id="global.anthropic.claude-haiku-5-5", region_name="us-east-1"),
    tools=[],                      # reads untrusted email → no tools, ever
    system_prompt=READER_PROMPT,
)
verdict = reader(email_text, structured_output_model=EmailVerdict).structured_output

# policy — two gates + escalation, auditable, cannot be prompted
receiver = config.receiver_address                              # the traffic-policy address from the stack context env var, never To/Cc
contact_by_name = graph.lookup(receiver, sender_name)             # display name only: gate 1 must not depend on the model
contact = contact_by_name or graph.lookup(receiver, verdict.claimed_person)   # gate 2 may use the Reader's claim
reasons = lists.lookup_sender_reasons(sender_address, sender_domain, sender_name, contact_names)   # code, DynamoDB rows; raises if the read fails
reasons += auth.reasons(headers)                                # exactly one X-Pidge-Auth, else "auth_tampered"; neither spf nor dkim = pass → "auth_failed"

# Gate 1: code-driven HOLD — no model can override this
address_known = contact and sender_address in contact.known_addresses
impersonator = contact_by_name and sender_address not in contact_by_name.known_addresses   # known display name, address not theirs
if impersonator:
    reasons.append("unknown_address")

# Gate 2: model-driven HOLD — original Reader check
model_hold = verdict.intent != "none" and verdict.confidence >= 0.6 and contact

# Escalation: Opus decides on unknown-address holds; flag off → no call, HOLD as if Opus agreed
escalation = None
if config.escalation_enabled and (impersonator or model_hold) and not address_known:
    escalation = escalate(email_text, EscalationFacts(gate_fired="gate_1" if impersonator else "gate_2", display_name_matches_contact=bool(contact_by_name), address_known=address_known, auth=headers.pidge_auth, reasons=reasons, reader_verdict=verdict.without_summary()))   # Claude Opus, EscalationVerdict, ~$0.03
    if escalation.failed:                                        # no access, throttling, invalid schema → stays HOLD
        reasons.append("escalation_failed")
    elif graph.lookup(receiver, escalation.claimed_person) != contact:   # same lookup as the Reader's claim: case and spacing ignored
        reasons.append("person_conflict")                        # two models name different people → stays HOLD
    elif model_hold and not impersonator and escalation.decision == EscalationDecision.WARN:
        model_hold = False; reasons.append("escalation_cleared")  # gate 2 only; gate 1 is code and never overridden

if impersonator or model_hold:
    friction = "double_tap" if impersonator and verdict.intent in ("money", "code") else "single_tap"
    req = requests.create(email_id, contact, verdict, ttl_seconds=60, friction=friction, escalation=escalation)   # REQUEST#.escalation
    ws.push(receiver, {"state": "hold", "request_id": req.id, "reasons": reasons, "friction": friction})
    sent = await asyncio.gather(rcs.ask(contact, req), whatsapp.ask(contact, req), inapp.ask(contact, req),
                                return_exceptions=True)        # one failed channel never cancels the hold
    requests.record_channels(req.id, sent)                      # channelsSent = the ones that returned a message id
    if not any_ok(sent):
        ws.push(receiver, {"state": "warn", "reason": "unreachable", "reasons": reasons})   # still never a release
elif "escalation_cleared" in reasons:
    emails.record_escalation(email_id, escalation)              # EMAIL#.escalation: no REQUEST# exists for a cleared email
    ws.push(receiver, {"state": "warn", "reason": "escalation_cleared", "reasons": reasons})   # WarnReason.ESCALATION_CLEARED: "Pidge checked twice; a ! mark, not a hold"
elif verdict.intent != "none" and not contact:
    ws.push(receiver, {"state": "warn", "reason": "unknown_name", "reasons": reasons})
elif verdict.intent != "none":
    ws.push(receiver, {"state": "warn", "reason": "low_confidence", "reasons": reasons})
elif reasons:
    ws.push(receiver, {"state": "warn", "reason": "listed_sender", "reasons": reasons})

Bedrock Guardrails runs on chat input (D4 revised 2026-10-23); on inbound email, later, a hit is reason prompt_attack, never a block. Prompt-injection trap named: the only free text that leaves the Reader is summary; code strips URLs and digits and caps it at 140 chars before it becomes the single WhatsApp template variable. Yes / No are fixed buttons, never parsed from text, and pidge-verdict writes them with a conditional update (first valid tap wins). The auth header the Reader sees is Mail Manager's own: a sender-written X-Pidge-Auth is dropped at ingress, a second copy adds the reason auth_tampered.

Hallucination guard: gate 1's code-driven HOLD fires on display name + unknown address — if the Reader is tricked into returning intent=none, the HOLD still happens. The Opus escalation can clear only a gate-2 hold, never gate 1, so a fooled Reader and a fooled Opus together still cannot switch gate 1 off. The ask card shows the sender address and subject from code (not the summary), so Jimin sees exactly who wrote and what the subject says. For impersonator payment asks, two taps instead of one.

Workflow Patterns

Each LangChain-style pattern as it appears in SendPidge, with the mechanism that implements it in the POC and the Strands primitive it maps to. Tags say what is actually built by Oct 28.

Sequential built

Lambda handler, top to bottom. Strands: a Graph with plain edges. One linear path, so no framework is needed for ordering.

Conditional built

Code if on structured_output. Strands: add_edge(a, b, condition=fn) — the condition is a plain callable, which is exactly where the Rule of Two wants the decision.

Parallel built 1 of 3 · RCS slice 5 · WhatsApp slice 6

asyncio.gather(…, return_exceptions=True) in the Lambda. Strands: ready nodes in a Graph batch run as concurrent tasks. The first valid answer wins by conditional write; a later No still overrides a Yes.

Human-in-the-loop built

Two Lambdas + DynamoDB state. Strands: an interrupt returns Status.INTERRUPTED and resumes with an interruptResponse; on Lambda the resume is the webhook, not a sleeping process.

Loop / retry pattern — shield at 10 min, re-ask once, then timeout

Slice 8: Amazon EventBridge Scheduler fires once ten minutes after the hold, re-asks over the same channels if the row is still pending, and marks timeout on the second expiry (20A–26A). Until then the backend marks timeout lazily. Strands: a Graph cycle with reset_on_revisit and set_max_node_executions. The PWA counts down and shows the shield; a long-press releases.

Tool-less agent (Rule of Two) built

Only typed fields cross the boundary. The thing that can send messages never reads the scammer's words. This is the line a judge should be able to point at.

Failure Modes

Haiku 5.5 access not granted in time

Swap model id to us.anthropic.claude-haiku-4-5. Same code path. Confirm exact ids in the console on day 1. Happened 2026-10-22; 4.5 is running.

Reader can't produce a valid verdict

WARN badge — "Pidge couldn't check this one" — plus a logged error. Never a silent pass: a classifier failure fails closed toward the user.

HTML part will not parse

Reason links_unreadable, WARN like a Reader failure; the body text and the Reader still run. Never a clean email because the link check failed.

pidge-reader crashes or times out

Async invocation retries twice, then the event lands in the SQS dead-letter queue and a CloudWatch alarm fires. A duplicate S3 delivery exits on the EMAIL# conditional put, so Jimin is never asked twice.

MX record not propagated

Drop a .eml into the S3 bucket by hand — the pipeline starts at the S3 event, so the demo still runs.

WhatsApp template rejected or late

WHATSAPP_ENABLED=false; RCS + in-app carry the demo; WhatsApp is the second CDS channel.

RCS tester invite never arrives, or the carrier does not deliver RBM to Jimin's phone

Korea is not an RCS launch country; the docs say testers work in any country, unverified on a Korean SIM. RCS_ENABLED=false, WhatsApp + in-app carry the demo; the code path stays and is shown in the README. Any mocked tap in the video is labelled as mocked.

Jimin silent for 10 min

Shield icon; email stays held; 5 s long-press releases. A late No still lands and shows the warning; a late Yes is ignored (the hold already expired).

One channel fails to send

The hold is already on Grandma's screen and the other channels carry it; channelsSent shows which went out. All three failing → WARN "Pidge couldn't reach Jimin", never a release.

Call-nudge offer fails or the nudge cap is hit

callNudge.status = offer_failed / capped, logged with metric WhatsAppSendFailed; the verdict push never waits for it. Reminder cannot be scheduled → reminder_failed; Grandma's in-app line still shows.

SES receipt fails (sandbox, unverified address)

Logged error; the verdict push to Grandma does not depend on it.

WebSocket drops

Poll DynamoDB every 3 s during an active hold only; auto-reconnect.

Reader hallucinates intent=none on a scam

Gate 1 (code-driven HOLD on name match + unknown address) catches it without the model. If the scam uses a name not in the trust graph, gate 1 does not fire — but this is a weaker attack (WARN only, by design). The Opus escalation decides hold or warn on gate-2 holds only; it cannot touch gate 1.

Reader picks the wrong claimed_person

The wrong person is asked and says No; Grandma is warned off the real person's email. On an unknown-address hold the Opus escalation adds person_conflict as a reason when it names someone else; the ask still goes to the Reader's contact, and the ask card shows the sender address from code so Jimin can recognise it.

Jimin taps Yes by mistake

The 10-second undo window holds the release. His screen shows "Undo?" for 10 s; an undo tap converts it to a No. A late No still overrides at any time.

Jimin taps No on his own email

He can tap "I made a mistake" within 5 min; the LIST#address row is removed and Grandma gets an updated notification. Without this, his address stays blocked.

Wrong phone number at setup

A stranger receives the ask and could tap Yes. Not mitigated in the Oct 28 build: contacts are seeded (verifiedVia: "seed"). Designed, not built: verification before the CONTACT# row is written (roadmap 2 Flow enrolment, 14 Notify OTP).

Case agent invents facts

Amounts, dates and deadlines in the recovery pack are filled from the lost-payment case (CASE# row) and the refund rules (RULE# rows, git-reviewed JSON with a source link per step). The model writes only the connecting sentences. Phone numbers come from "the number on the back of your card." Grandma confirms each fact before acting.

Opus escalation call fails

No access, throttling or an invalid schema → HOLD with escalation_failed; never WARN, never PASS.

A user prompt-injects the chat

Guardrails refuses it before the agent. If it slips through, every tool is scoped to the caller's userId from the token and there is no query or scan tool, so the worst outcome is bad advice to the person who typed it. Red-team cases in test_chat.py.

Guardrail unavailable, chat over the hourly cap, or no SpeechRecognition

Refusal, never a bypass (fails closed); CHAT_ENABLED=false hides the composer. Without SpeechRecognition the mic is hidden and typing works; SendPidge never receives audio, and dictation audio goes only to the browser vendor's speech service.
