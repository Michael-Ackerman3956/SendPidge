SendPidge — Technical Spec

Round 2 · approved 2026-10-21 · AWS CDS Agentic AI Partner Hackathon · deadline 2026-10-28

How This Works

SendPidge is a PWA (a website that installs like an app) with an AI agent called Pidge. When an email arrives claiming to be someone you know and asking for money, Pidge holds it and asks the real person "was this you?" on a channel only they control. Their answer lands on your screen in seconds.

Inside AWS: Amazon SES Mail Manager receives the email and writes it to S3. A Strands agent on AWS Lambda reads it with Claude Haiku 5.5 on Amazon Bedrock and returns a typed verdict. That reader has no tools — it only ever sees the untrusted text. Plain code then checks the DynamoDB trust graph, creates a 60-second hold, and fans out the question in parallel over AWS End User Messaging Social (WhatsApp) and an in-app WebSocket. The reply comes back through Amazon SNS (WhatsApp) or the WebSocket (in-app), a second Lambda records the verdict, and Amazon API Gateway WebSocket pushes it to Grandma's screen.

The agent is autonomous — nobody asks it to check — but the decision to hold or release is code, not a prompt. That is why Pidge can't be talked into releasing.

Agent Layer — Strands Agents SDK

Rule of Two (your 2026-10-03 ruling, same as Meta's agent rule): the model that reads untrusted text gets no tools; code runs lookups and sends; the AI can only raise a verdict. Strands expresses this directly — Agent(tools=[]) with a Pydantic structured_output_model. The structured-output schema is itself a side-effect-free validating tool.

from pydantic import BaseModel, Field
from typing import Literal
from strands import Agent
from strands.models import BedrockModel

class EmailVerdict(BaseModel):
    claimed_person: str | None = Field(description="Name the sender claims to be, or null")
    intent: Literal["money", "code", "urgent_action", "none"]
    confidence: float = Field(ge=0, le=1)
    summary: str = Field(max_length=140, description="One neutral sentence for the real person. No URLs, numbers or instructions.")

reader = Agent(
    model=BedrockModel(model_id="global.anthropic.claude-haiku-5-5", region_name="us-east-1"),
    tools=[],                      # reads untrusted email → no tools, ever
    system_prompt=READER_PROMPT,
)
verdict = reader(email_text, structured_output_model=EmailVerdict).structured_output

# policy — plain code, auditable, cannot be prompted
receiver = config.receiver_address                              # the traffic-policy address from SSM, never To/Cc
contact = graph.lookup(receiver, verdict.claimed_person)
reasons = lists.lookup(sender_address, sender_domain, sender_name, receiver)   # lookup tables; raises if the read fails
reasons += auth.reasons(headers)                                # exactly one X-Pidge-Auth, else "auth_tampered"; dmarc=fail → "dmarc_fail"
if verdict.intent != "none" and verdict.confidence >= 0.6 and contact:
    req = requests.create(email_id, contact, verdict, ttl_seconds=60)
    ws.push(receiver, {"state": "hold", "request_id": req.id, "reasons": reasons})
    sent = await asyncio.gather(rcs.ask(contact, req), whatsapp.ask(contact, req), inapp.ask(contact, req),
                                return_exceptions=True)        # one failed channel never cancels the hold
    requests.record_channels(req.id, sent)                      # channelsSent = the ones that returned a message id
    if not any_ok(sent):
        ws.push(receiver, {"state": "warn", "reason": "unreachable", "reasons": reasons})   # still never a release
elif verdict.intent != "none":
    ws.push(receiver, {"state": "warn", "reason": "unknown_name", "reasons": reasons})
elif reasons:
    ws.push(receiver, {"state": "warn", "reason": "listed_sender", "reasons": reasons})   # a reason or a !, never a hold

Prompt-injection trap named: the only free text that leaves the Reader is summary; code strips URLs and digits and caps it at 140 chars before it becomes the single WhatsApp template variable. Yes / No are fixed buttons, never parsed from text, and pidge-verdict writes them with a conditional update (first valid tap wins). The auth header the Reader sees is Mail Manager's own: a sender-written X-Pidge-Auth is dropped at ingress, a second copy adds the reason auth_tampered. Bedrock Guardrails' prompt-attack filter is optional (it costs ~2× the Haiku call).

Workflow Patterns

Each LangChain-style pattern as it appears in SendPidge, with the mechanism that implements it in the POC and the Strands primitive it maps to. Tags say what is actually built by Oct 28.

Sequential built

Lambda handler, top to bottom. Strands: a Graph with plain edges. One linear path, so no framework is needed for ordering.

Conditional built

Code if on structured_output. Strands: add_edge(a, b, condition=fn) — the condition is a plain callable, which is exactly where the Rule of Two wants the decision.

Parallel built 2 of 3

asyncio.gather(…, return_exceptions=True) in the Lambda. Strands: ready nodes in a Graph batch run as concurrent tasks. The first valid answer wins by conditional write; a later No still overrides a Yes.

Human-in-the-loop built

Two Lambdas + DynamoDB state. Strands: an interrupt returns Status.INTERRUPTED and resumes with an interruptResponse; on Lambda the resume is the webhook, not a sleeping process.

Loop / retry pattern — POC shows shield at 60 s

Later: Amazon EventBridge Scheduler re-dispatches on timeout. Strands: a Graph cycle with reset_on_revisit and set_max_node_executions. POC: the PWA counts down and shows the shield; a long-press releases.

Tool-less agent (Rule of Two) built

Only typed fields cross the boundary. The thing that can send messages never reads the scammer's words. This is the line a judge should be able to point at.

No on-device LLM is possible for a PWA on iPhone. AWS SageMaker Edge Manager was discontinued (2024-04); Greengrass targets IoT boxes; Chrome's Prompt API is desktop-only; Apple Foundation Models is a Swift API with no Safari surface. A native app later would unlock Apple's on-device 3B model.

Honest math: tiering saves ~67% of model cost, which is $15 vs $5 per 100K emails. T0 is the tier that matters. Decisions — your call, my pick first

D1 · How much Strands?

Pick: Strands Agent for the Reader only; orchestration in code. Fewer LLM calls, Jimin's phone buzzes faster, policy is auditable, and it is exactly the Rule of Two. OTel traces of the Reader still show in the demo.

Alternative: a Strands Graph Reader → Composer (both tool-less; Composer writes Jimin's and Grandma's Korean sentences). +1–2 s, +$0.0002/email, more "graph" to show judges. Composer is the first "later".

D2 · Lambda or AgentCore Runtime?

Pick: AWS Lambda with the official Strands layer. You know the Cloud Functions model; 7 days; 5 new services already.

Alternative: Amazon Bedrock AgentCore Runtime — the box judges saw labelled "(NEW)" in the sample; 8-hour sessions could hold the 60 s wait; needs a container, ECR, IAM, and InvokeAgentRuntime. The Reader code is identical either way, so it is a deploy-time swap later.

D3 · Model per tier

Pick: Haiku 5.5 for everything in the POC. Request model access on day 1 (not open by default). Nova Micro as T1 later; Gemma 4 E2B wired as a stub reader (untested in the POC); T0 heuristics later.

Fallback if access is late: us.anthropic.claude-haiku-4-5 — same Converse + structured output, 10× the price, trivial at POC volume.

D4 · Bedrock Guardrails prompt-attack filter?

Pick: skip for the POC. It costs ~$0.00048 per email — twice the Haiku call — and the tool-less Reader is the real defence. The AWS chat-orchestrator sample also sets PROMPT_ATTACK: NONE.

Later: apply only to T0-flagged mail.

D6 · RCS as the third real channel decided 2026-10-21

Built, not stubbed. The stub assumed "registration takes days"; the AWS docs show a testing registration approved in minutes with no carrier approval, the full API, and delivery to tester phones in any country. Rich card + Yes/No chips via SendRcsMessage, taps via the two-way SNS topic, same asyncio.gather and the same verdict handler.

Not built: SMS fallback (needs an SMS number). Risk: Korea is not a launch country and RBM delivery to a Korean tester SIM is unverified → RCS_ENABLED flag, day-1 check with the phone in hand.

D5 · Lookup tables as a semi-stub?

Pick: yes — sender-side only. Known-bad sender domains and lookalike names checked against Grandma's own contacts, ~20 hand-written sample rows, a reason or a ! mark, never a hold. Confirm writes the first real row. Tier 1–3 feeds come after the hackathon through MailPidge's @mailpidge/link-intel module in its reasonsOnly policy. Closes a PRD gap: prd.md > What We're Building lists lookalike sender detection, which this spec had parked in T0 "later".

Alternative: skip entirely; lookalike moves to T0 later and pidge-verdict writes nothing on Confirm. Body links and URL safety stay cut either way (scope.md > Explicitly Cut).

Decided by evidence (say if you disagree): Amazon SES Mail Manager instead of classic receipt rules · Amazon SNS is back for WhatsApp replies (that is how EUM Social delivers inbound) · exact names "AWS End User Messaging Social / SMS" · Python for the agent Lambda (TS SDK has Graph but no GA statement) · a classifier failure shows WARN, never a silent pass (your no-silent-fallback rule) · dead-letter queue + alarm on the email trigger, idempotent EMAIL# write, per-user token on WebSocket $connect, retention rules in CDK, IAM scoped to the phone-number ARN, config in SSM Parameter Store, pytest on policy / sanitizer / lists / verdict — the gaps a code-reading judge would flag against the AWS sample repos.

Deck review fixes (2026-10-21, four read-only reviewers over the three pre-interview decks): Confirm writes LIST#address, not the domain · conditional verdict write with No-beats-Yes and message-id dedupe (late replies settled: No lands any time, Yes only while pending) · hold pushed before gather(…, return_exceptions=True) · X-Pidge-Auth dropped at ingress if pre-written and parsed in code · email body rendered as text under a CSP · SES SendEmail receipt to Jimin so one SES call runs at demo time. Ruled out: Nostr / Matrix / passkeys (Later — both sides must enrol, and RCS and WhatsApp buttons cannot carry a signature), redaction of the held body, a HOLD floor in code (a fooled Reader gets WARN, keeping the 2026-10-05 "lists never verdicts" ruling).

Build-time hardening from the same review (sharpen existing steps, no new steps):

Reader step — confidence described as "how clearly the email asks for this intent", never "how fake the sender looks"; READER_PROMPT cues in EN/KO (secrecy, "phone broke / new number", new payee, today deadline, "send the code back", remote-access app, "contact me on another app" → urgent_action); body wrapped in a random boundary tag the prompt names as data.

Lookup-tables step — reasons for a display name containing an address, Reply-To domain ≠ From domain, a known contact name from an address not on the CONTACT# row ("Jimin doesn't usually write from this address"); a money/code/secrecy keyword hit with a known name is a reason (WARN), not a hold.

CDK step — ask cap of 3 open requests per contact per hour (over the cap: keep the hold, send nothing, never PASS); AWS Budgets alarm; reserved concurrency on pidge-reader; one IAM role per Lambda (pidge-verdict gets no S3 read and no Bedrock); aws:SourceAccount / aws:SourceArn on both SNS topic policies and the sms-voice two-way role; $connect token stored hashed, compared in constant time, out of access logs; logs and OTel spans carry ids, enums and reason codes only — check one real Strands trace for prompt text.

Swarm step (build item 6) — eight grounded templates (phone-broke from a friend's address EN + KO · code-only ask · hijacked real address with auth pass · post-voice-clone "bail by 3 pm" · AI-personalised lure · lookalike sender + gift card / crypto ATM · injection pack: visible line, hidden HTML comment, fake JSON verdict, coaching to hold Cancel) plus two benign controls (real Jimin gift email → HOLD then Yes; family chat with no ask → PASS); assert no number, URL or address from the email reaches any outbound payload; run with RCS / WhatsApp off or an in-app-only receiver; report hold rate and false holds.

Day-1 step — WhatsApp template message_send_ttl_seconds = 60, no "verify your identity" wording (Meta files it as authentication), metaApiVersion ≥ v21; preflight script (Haiku access, template APPROVED + UTILITY, both SNS topics subscribed, RCS tester ACTIVE, MX on its own hostname, SES identities verified); LICENSE and a prior-work note (MailPidge icon and theme) in the README; copy never says "safe" — "Jimin says he sent this"; "emergency contact", not "guardian".

Components

PWA Shell

Omni-inbox (email real, 3–4 mock rows for SMS/notifications added last), email detail, Pidge hold overlay (60 s countdown, 5 s long-press cancel, shield on timeout), onboarding, verification card for Jimin. Hosted on S3 (+ CloudFront optional). The email body is shown as text only (textContent of the HTML-stripped body from pidge-reader, never innerHTML); no remote images, so no tracking pixel tells the sender she opened it and no injected markup can imitate the verdict screen or read the WebSocket token. CSP: default-src 'self'; img-src 'self' data:; connect-src wss://….

Mail Manager Inbound

Ingress endpoint (OPEN) → traffic policy (ALLOW recipient, DROP rest) → rule set: rule 1 Drop when the MIME header X-Pidge-Auth already exists (a sender cannot pre-write the verdict), rule 2 add header X-Pidge-Auth from SPF/DKIM/DMARC verdicts, Write to S3. pidge-reader reads it with get_all; anything but exactly one value is the reason auth_tampered (covers whether Add header appends or replaces, unverified). CDK via AWS::SES::MailManagerIngressPoint / TrafficPolicy / RuleSet. You create the MX record from the stack output.

PRD ref: prd.md > Message Detection

pidge-reader (Lambda + Strands)

S3 event → parse .eml → Reader agent (tools=[], Haiku 5.5, structured output) → policy code → DynamoDB request → WebSocket "hold" → parallel ask with return_exceptions=True → channelsSent. The hold goes out before the fan-out, so one failed channel never turns a live hold into a WARN; only all three failing does. ≥512 MB / 60 s timeout (inference; the docs example is 128 MB / 30 s). Async S3 invocation: retries twice, then an on-failure destination → SQS dead-letter queue + CloudWatch alarm, never a silent drop. Idempotent: EMAIL#<s3Key> written first with attribute_not_exists; a duplicate event exits before the Reader.

PRD ref: prd.md > Hold and Verify

Trust graph (DynamoDB)

Single table. RECEIVER#email / CONTACT#name rows hold the real person's WhatsApp number, PWA connection id and email. REQUEST#id rows hold status and expiry. EMAIL#id rows hold s3Key, authVerdict, flagged, quarantined.

Retention, set in CDK: raw .eml deleted after 30 days by an S3 lifecycle rule unless tagged quarantine=true (kept 1 year, then Glacier Deep Archive); DynamoDB TTL on REQUEST# 30 d, CONN# 1 d, EMAIL# 90 d (quarantined rows exempt); LIST# rows carry expiresAt and are replaced on sync — a stale feed reads as unavailable, never clean; CloudWatch logs 14 d, X-Ray 30 d. Storage is cheap; logs and requests are what grow.

WhatsApp channel (EUM Social)

SendWhatsAppMessage with a pre-approved template (one variable: summary; buttons Yes / No with payload req-id:yes|no). Sandbox: 5 registered numbers. Inbound: WABA event destination → SNS → pidge-verdict, which must parse interactive.button_reply.id (the AWS sample parses only text.body). In-app channel (API Gateway WebSocket)

One WebSocket API. $connect requires a per-user token issued at onboarding (stored on the RECEIVER# / CONTACT# row); ws_connect rejects anything else and takes userId from the matched row, never from the client. Grandma's connection receives hold → verdict. Jimin's connection receives the verification card and sends Yes/No on $default. Connection ids stored in DynamoDB. Web Push (VAPID) wakes the PWA on iOS 16.4+.

PRD ref: prd.md > Verification to Real Person

pidge-verdict (Lambda)

Triggers: SNS (RCS two-way topic, WhatsApp topic) and WebSocket $default (in-app, Confirm tap). One parser per channel — RCS postbackData, WhatsApp interactive.button_reply.id, in-app body — all yielding req-id:yes|no. Validates request id and that the sender matches the contact's channel. Writes the status with a conditional UpdateItem: No beats Yes — a No is accepted at any time, even after a Yes or the timeout, and sets denied; a Yes needs status = pending AND expiresAt > now and sets confirmed; a failed condition means the first valid tap already won (three channels make two taps normal) and the duplicate is logged, never applied. Each channel's message id (RCS inboundMessageId, WhatsApp wamid) is stored on the request so a redelivered SNS record exits. Then: SES SendEmail receipt to contactEmail ("Your answer was recorded; the email to Grandma stays held / was released"), never to the monitored address so nothing re-enters pidge-reader; pushes verdict to Grandma; on Confirm tags the S3 object, marks quarantined and writes one LIST#address row for the sender's full address (source: pidge-confirmed) — the address, never the registrable domain, because one gmail.com scam would otherwise mark every Gmail sender including real Jimin. The only new code the lookup tables add to the real flow.

PRD ref: prd.md > Verdict and Resolution

Lookup tables (semi-stub)

Sender-side only: known-bad sender domains/addresses plus lookalike detection against Grandma's own contact names (confusable skeleton + edit distance ≤ 1 — "JImin", Cyrillic "Jіmin"). shared/lists.py reads LIST# rows from the same table and returns reasons; policy code decides what to show. A match adds a reason or a ! mark, never a hold, never a pass (your 2026-10-05 ruling: lists add reasons, never verdicts). A failed read raises → the same WARN as a Reader failure; unavailable is never clean.

POC data: ~20 hand-written rows in infra/seed/lists.sample.json (the demo's lookalike domain, invented brand-hyphen domains, a ~30-entry confusables map), all source: "sample" and labelled sample in the UI. No real feed is seeded in the POC, and real list data never lives in the repo (open-core ruling). Only commercial-OK sources are ever registered; each carries a licence tag, as in MailPidge's registry guard.

Data tiers (not the AI tiers above): tier 0 pidge-confirmed (written on Confirm — the demo adds the first real row) · tier 1 free commercial-OK feeds (Phishing.Database MIT · KISA phishing sites · AMF blacklist, Licence Ouverte) · tier 2 live lookup (Google Web Risk Lookup, ~100k lookups/month free · RDAP domain age) · tier 3 paid (Spamhaus DQS DBL · APWG eCX · OpenPhish Premium · urlscan.io). Tiers 1–3 arrive after the hackathon via MailPidge @mailpidge/link-intel (reasonsOnly policy; POST /v1/link-intel/check, LINK-INTEL-1.24, default off) or by writing the same row shape. Body links and URL safety stay cut.

RCS channel (EUM SMS · RCS agent)

Built. One AWS RCS Agent with a testing registration (TEST_RCS_LAUNCH_REGISTRATION): no carrier approval, approved in minutes, full API, delivery only to phones added as testers (create-verified-destination-number --rcs-agent-id; invite from "RBM Tester Management" in 2–20 min, on iPhone under Unknown Senders → "Make me a tester"). Setup script infra/scripts/rcs_agent_setup.sh follows the AWS sample: agent → registration → logo 224×224 + banner 1440×448 → 23 field values (privacy + terms URLs from edge/public/, accent colour ≥ 4.5:1 on white, billingCategory set) → submit → poll TestingAgent.Status: ACTIVE. Two-way: update-rcs-agent --two-way-enabled --two-way-channel-arn <SNS> --two-way-channel-role <role>.

Send: send_rcs_message with a VERTICAL RichCard ("Was this you?", sanitised summary, Pidge image) and two Reply suggestions, PostbackData req-id:yes|no, TimeToLive=60. Limits: chip text ≤ 25 chars, ≤ 11 suggestions. Direct-to-agent sends are RCS-or-nothing; SMS fallback needs a separate SMS number, so it is not built (in-app and WhatsApp are the fallback).

Inbound: taps arrive only on the two-way SNS topic as messageBody JSON {"type":"SUGGESTION","text":"No","postbackData":"req-id:no"}; pidge-verdict routes on postbackData, never on display text. Test messages cost the standard RCS rate per delivered message; whether a testing agent incurs launch fees is unverified (check the bill on day 2). Research: devpost/research/research_aws_rcs.md.

Failure Modes

Haiku 5.5 access not granted in time

Swap model id to us.anthropic.claude-haiku-4-5. Same code path. Confirm exact ids in the console on day 1.

Reader can't produce a valid verdict

WARN badge — "Pidge couldn't check this one" — plus a logged error. Never a silent pass: a classifier failure fails closed toward the user.

pidge-reader crashes or times out

Async invocation retries twice, then the event lands in the SQS dead-letter queue and a CloudWatch alarm fires. A duplicate S3 delivery exits on the EMAIL# conditional put, so Jimin is never asked twice.

MX record not propagated

Drop a .eml into the S3 bucket by hand — the pipeline starts at the S3 event, so the demo still runs.

WhatsApp template rejected or late

RCS + in-app carry the demo; WhatsApp is the second CDS channel.

RCS tester invite never arrives, or the carrier does not deliver RBM to Jimin's phone

Korea is not an RCS launch country; the docs say testers work in any country, unverified on a Korean SIM. RCS_ENABLED=false, WhatsApp + in-app carry the demo; the code path stays and is shown in the README. Any mocked tap in the video is labelled as mocked.

Jimin silent for 60 s

Shield icon; email stays held; 5 s long-press releases. A late No still lands and shows the warning; a late Yes is ignored (the hold already expired).

One channel fails to send

The hold is already on Grandma's screen and the other channels carry it; channelsSent shows which went out. All three failing → WARN "Pidge couldn't reach Jimin", never a release.

SES receipt fails (sandbox, unverified address)

Logged error; the verdict push to Grandma does not depend on it.

WebSocket drops

Poll DynamoDB every 3 s during an active hold only; auto-reconnect.

Simplified on purpose

Timeout counted in the PWA, backend marks timeout lazily on the next reply or read (a late No still applies, a late Yes does not) — no EventBridge Scheduler yet.

Orchestration in code, not a Strands Graph — one agent, one decision.

SMS fallback not built; RCS, WhatsApp and in-app are real. FallbackConfiguration needs a separate SMS number, and in-app already covers a phone without RCS.

Omni-inbox mock rows last; email-only inbox proves the kernel.

No auth — Grandma and Jimin are pre-provisioned.
